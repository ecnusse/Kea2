# Kea2 Agent 专业知识维护指南

本指南面向维护 Kea2 测试分析知识的团队成员，介绍知识条目的统一格式、编写方法、更新流程和验证方法。

## 1. 专业知识的作用

专业知识帮助 Agent 正确解释 MCP 返回的实验数据，主要用于规范报告第九部分“分析与建议”：哪些现象值得分析、满足什么条件才能作出判断、哪些结论不能下，以及什么建议具有实际价值。

专业知识不是实验事实。某条知识描述了可能发生的问题，不代表当前实验发生了该问题；应用规则前，Agent 必须核对本次任务的 MCP 数据。

前八部分继续按报告模板展示结果，不需要逐条解释知识、统计公式或判断过程。知识条目可以规定某种正常现象不应触发分析，但不应随意改变统计口径、填补未知数值或增加报告章节。

## 2. 文件与格式

知识集中维护在 [domain-knowledge.md](../skills/kea2-result-analysis/references/domain-knowledge.md)，使用 **UTF-8 编码的 Markdown**，可以用中文或英文编写。

每条知识采用一个二级标题，下面固定使用六个三级标题：

| 标题 | 应填写的内容 |
| --- | --- |
| 适用范围 | 适用的检查项、测试模式、运行状态、应用或版本范围 |
| 专业知识 | 相关机制或领域经验；区分确定机制与经验判断 |
| 所需数据与判断条件 | MCP 工具、section、具体字段、适用条件，以及数据不足时的处理 |
| 分析规则 | 可以得出的结论、不能得出的结论，以及需要额外证据的解释 |
| 报告输出要求 | 何时值得写入第九部分、如何表达、哪些说明应省略 |
| 后续建议 | 满足条件时可以建议的具体行动；无必要建议时写“无” |

### 编号规则

使用 `KEA-类别-三位编号`，例如 `KEA-PROP-001`。同一类别内顺序编号，修改同一条知识时保留编号，不重复使用已经分配的编号。

| 类别 | 内容 |
| --- | --- |
| PROP | 性质执行、违反和执行错误 |
| INV | 不变量及其异常 |
| COV | Activity、Widget 覆盖情况及趋势 |
| CRASH | Crash 或 Crash/ANR 共用机制 |
| ANR | ANR 专项判断 |
| GENERAL | 跨类型的通用分析规则 |

同一知识只维护一份，相关条目可以通过编号引用，避免不同位置出现相互矛盾的描述。废弃条目应注明替代编号或通过版本记录保留变更原因。

## 3. 可复制的条目模板

以下六个部分都应保留；没有适用内容时明确写“无”或“不适用”及必要原因。

```markdown
## KEA-<类别>-<编号> · <知识标题>

### 适用范围
<适用的检查项、测试模式、运行状态、应用或版本范围。>

### 专业知识
<说明机制或领域经验。经验性判断应说明适用前提，不写成必然因果。>

### 所需数据与判断条件
- 通过 <MCP 工具及 section> 获取 <具体字段或证据>。
- 当 <条件> 同时成立时，应用本条知识。
- 数据不足或条件无法核对时，<如何处理>。

### 分析规则
- 可以判断：<有依据的结论>。
- 不能仅凭这些数据判断：<需避免的结论>。
- 需要额外证据：<如有，列出需要核对的信息>。

### 报告输出要求
- <什么时候值得在第九部分输出分析，如何表达。>
- <哪些常规说明应省略；不适用时不要强行输出。>

### 后续建议
<与证据对应的具体检查或改进建议；没有必要建议时写“无”。>
```

## 4. 编写原则

1. **每条解决一个判断问题。** 例如“前置条件满足但性质未执行”，不要在同一条中混入所有性质与覆盖率知识。
2. **写出可核对的条件。** 使用实际 MCP 字段，注明单位和必要范围。不要仅写“覆盖率比较低”“执行次数不正常”。阈值需要团队依据，不能为了让规则完整而随意设定。
3. **区分机制、观察和假设。** “Kea2 如何记录数据”属于机制；“本次计数是多少”来自 MCP；“可能由什么原因造成”需要进一步证据。
4. **数据不足时不强行应用。** 缺失、不适用和零值不能混为一谈。新知识需要的数据若当前 MCP 无法提供，应先明确数据需求，不要求 Agent 绕过 MCP 读取源码、HTML 或原始文件。
5. **正常现象不必分析。** 规则可以用于阻止错误分析，不一定要生成一段解释。尤其不要把“专业知识”原文机械复制到报告中。
6. **建议要有对应依据。** 每个建议应说明要解决什么问题、如何验证。没有实际价值时写“无”，不要固定建议延长测试或重跑。
7. **应用专属知识要限定范围。** 写清包名、已知版本或业务条件，避免套用到其他应用。

编写者可以在“专业知识”中注明机制依据、团队认可的经验来源或文档链接。机制研究与条目维护不等于允许分析 Agent 自行读取实验源码；报告中的实验事实仍只来自 MCP。

## 5. 示例：无异常时不生成崩溃日志

以下示例说明如何组织条目，尚不代表已将该规则加入实际加载的知识文件。

```markdown
## KEA-CRASH-001 · 无异常时不生成崩溃日志

### 适用范围
正常完成、MCP 返回 Crash 和 ANR 次数均为 0，且没有矛盾异常记录的实验。

### 专业知识
Crash/ANR 日志按异常产生。
没有发生 Crash/ANR 时，不生成对应日志属于正常行为。

### 所需数据与判断条件
- 通过 kea2_get_report 核对 execution.status 为 completed。
- summary.observed_crash_occurrences 和 summary.observed_anr_occurrences 均为 0。
- kea2_query_report 的 findings 中，crash/anr 记录与上述结果一致；
  查询范围足以核对，不能把未读分页当作没有记录。
- 计数为 null、文件读取失败或记录矛盾时，不应用本条正常零异常解释。

### 分析规则
- 不能仅因崩溃日志不存在，就判断实验数据缺失或采集异常。
- 文件读取失败、格式损坏和实验中断需要按具体情况处理。
- 结论针对本次实验，不扩展成应用在所有场景中都没有缺陷。

### 报告输出要求
- 结果部分正常展示 Crash：0、ANR：0，详情为“无”。
- 不因日志不存在，在第九部分追加缺失说明或泛化免责声明。
- 没有其他相关问题时，不单独生成分析段落。

### 后续建议
无。不能仅因日志不存在，建议修复日志采集或重新测试。
```

“专业知识”说明为什么这样判断，“报告输出要求”说明哪些内容值得展示。内部判断边界不需要自动变成面向用户的免责声明。

## 6. 如何验证知识是否生效

用明确的 `task_id` 重新分析已有实验，通常不需要重新执行设备测试。为每条重要规则准备以下情况：

| 情况 | 预期行为 |
| --- | --- |
| 条件满足 | 采用正确解释；按输出要求决定是否生成分析文字 |
| 条件不满足 | 不套用规则，不扩展到其他场景 |
| 数据不足或有矛盾 | 不强行给结论，指出真正影响判断的信息缺口 |

验证时可以对 Agent 说：

> 请使用 kea2-result-analysis 分析任务 `<实际 task_id>`。另外列出本次采用的专业知识编号、对应 MCP 条件及未满足的条件，供我核对规则是否正确应用。

核对信息用于维护验证，不要求每份正式报告都展示。检查最终报告是否减少错误推断、遗漏重要问题或产生新的无效解释。对要求“正常情况不输出分析”的条目，正确地省略内容同样是生效表现。

验证效果取决于实际客户端和模型；Markdown 校验只能检查形式，不能代替报告行为验证。

## 7. 与其他文件的分工

| 文件 | 维护内容 |
| --- | --- |
| `SKILL.md` | 何时读取知识、如何查询结果、如何完成分析流程 |
| `data-semantics.md` | MCP 字段含义、统计口径及数据限制 |
| `domain-knowledge.md` | 领域机制、判断条件、分析边界和建议规则 |
| `report-template.md` | 九部分结构、表格列和结果展示规则 |

保持这些职责分工，使专业知识能够独立更新，同时避免把同一判断规则复制到多个位置维护。
