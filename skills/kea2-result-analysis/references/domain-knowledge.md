# Kea2 实验分析知识

适用于结果契约 1.5。每条知识都要与当前任务、当前快照中的 MCP 记录核对。知识编号用于内部核对解释依据；观测值须以 MCP 返回的检查项及来源为依据。报告默认使用易读的解释，仅在用户要求溯源时展示知识编号及来源标识。来源不完整时，结论仅限于可读记录。如有无法核对的条件，保留原因未确定。

## KEA-PROP-001 · Property 未执行

### 适用范围

包含性质测试、`checks` 中明确标为 `kind=property` 且 `executed=0` 的检查项。不适用于纯自动探索，也不适用于已经执行过的性质。

### 专业知识

分析性质未执行时，首先检查前置条件是否曾经满足。前置条件满足过但性质未执行，可能是测试时间不足；前置条件从未满足，则需要考虑检查前置条件是否正确。

这两种情况提供排查方向，不直接证明测试时间不足或前置条件有误。

### 所需数据与判断条件

- 通过 `kea2_query_report` 的 `checks` 获取同一性质的 `kind`、`executed` 和 `precond_satisfied`，确认统计来源完整可读。
- `kind=property` 且 `executed=0` 时，再按 `precond_satisfied` 是否大于 0 分支分析。
- 结合 `kea2_get_report` 的运行状态、实际耗时及 MCP 返回的配置判断本次实验范围；配置时长不能冒充实际运行时间。
- 前置条件计数缺失、来源不完整或数据矛盾时，不将未知值当作 0，不强行选择分析分支。

### 分析规则

- `precond_satisfied>0`：说明前置条件曾满足，但性质尚未执行。测试时间不足是一种可能原因，不能直接认定调度失败或脚本故障。
- `precond_satisfied=0`：说明本次没有满足前置条件的记录，可以建议核对前置条件是否正确。不能仅凭这一计数断言条件写错，也不能排除探索尚未到达满足条件的状态。
- 不设置没有依据的“测试时间过短”阈值，不把计数差异换算成被浪费的执行机会。
- 若有 MCP 提供的相关覆盖或步骤证据，可以辅助解释；不能仅凭 Activity 名称猜测它与前置条件的关系。

### 报告输出要求

- 前面的结果部分只展示统计值；有实际未执行性质时，在第九部分按上述分支给出简短分析。
- 满足过前置条件时，可以写：“该性质的前置条件曾满足，但本次未执行，可能与测试时间不足有关。”
- 前置条件从未满足时，可以写：“该性质本次未满足前置条件，建议核对前置条件是否正确。”
- 将原因写为可能性或排查方向，不写成已经证实的根因；没有必要时不重复解释统计口径。

### 后续建议

- 前置条件满足过但未执行：可以建议延长测试时间，并观察该性质是否开始执行。
- 前置条件从未满足：可以建议用户核对前置条件的正确性，必要时确认探索是否到达目标状态。
- 以上是后续建议，不授权 Agent 自行读取或修改脚本、直接启动新测试。当前分析仍只使用 MCP 实验数据。

## KEA-INV-001 · Invariant 的 Fail 和 Error 均为零

### 适用范围

正常完成的包含不变量检查的实验；`checks` 中明确标为 `kind=invariant`，且该不变量的 `fail=0`、`error=0`，没有矛盾异常记录。不适用于未加载不变量的纯自动探索。

### 专业知识

不变量用于检查测试过程中各状态应保持的性质。对于正常完成、统计完整的不变量检查，Fail 和 Error 均为零表示本次检查通过，即本次测试中所有实际检查到的状态均通过。

不变量只统计 Fail 和 Error，不记录前置条件满足次数、执行次数或通过次数。缺少这些计数是统计设计，不应据此怀疑检查没有运行。

### 所需数据与判断条件

- 通过 `kea2_get_report` 确认 `execution.status=completed`，并通过 MCP 运行配置和检查项确认实验包含不变量。
- 通过 `kea2_query_report` 的 `checks` 核对目标项 `kind=invariant`、`fail=0`、`error=0`，统计来源完整可读。
- 对应不变量的异常记录不得与零异常统计矛盾；如需核对，查询 `findings`，使用 `type=invariant` 和 `check_name`。
- 未加载不变量、运行中断、数据缺失或部分可读、计数为 null 或存在矛盾记录时，不直接给出本条通过结论。

### 分析规则

- 条件满足时，可判断该不变量在本次测试所有实际检查到的状态中通过。
- “所有状态”限定为本次测试实际检查到的状态，不扩展为未探索状态、未来运行或应用全部可能状态。
- 不因执行次数或通过次数不适用，就推断不变量未执行或要求补查执行次数。
- 不从零 Fail/Error 推导检查过多少次、通过多少次或通过率。
- 任一 Fail/Error 大于 0 时，不适用本条零异常规则，应读取对应异常详情进行分析。

### 报告输出要求

- 统计表保留名称、Fail 和 Error，不增加执行或通过次数列。
- 需要总结不变量结果时，可以写：“该不变量在本次测试所有实际检查到的状态中均通过。”
- 不追加“无法证明不变量执行过”“缺少执行次数所以不能判断通过”等常规说明。
- 正常通过不要求在第九部分单独展开分析；如需整体总结，简洁说明结果即可，不反复添加泛化免责声明。

### 后续建议

无。不能仅因不变量不统计执行或通过次数，就建议补充计数、排查未执行或重新测试。

## KEA-CRASH-001 · 无异常时不生成崩溃日志

### 适用范围

正常完成、MCP 返回 Crash 和 ANR 次数均为 0，且没有矛盾异常记录的实验。适用于纯自动探索和包含性质测试的实验。

### 专业知识

Crash/ANR 日志按异常产生。没有发生 Crash/ANR 时，不生成对应的 `crash-dump.log` 属于正常行为，该文件不是每次实验都必须存在的结果文件。

因此，可选日志不存在与日志读取失败、格式损坏是不同情况，不能仅凭 `availability.crashes=missing` 就判断采集异常。

### 所需数据与判断条件

- 通过 `kea2_get_report` 核对 `execution.status=completed`。
- `summary.observed_crash_occurrences` 和 `summary.observed_anr_occurrences` 均为 0。
- 通过 `kea2_query_report` 的 `findings` 分别核对 `type=crash` 和 `type=anr`，返回总数均为 0，且与概览属于同一快照。不能把尚未读取的记录当作不存在。
- 运行信息中没有与零异常矛盾的标记；若 `execution.finding_flags.crash_or_anr=true`，不应用本条规则。
- Crash/ANR 日志来源为 `available` 或 `missing`。计数为 null、来源部分可读、读取失败、格式损坏或记录矛盾时，不应用本条正常零异常解释，也不自行将未知计数改成 0。

### 分析规则

- 满足上述条件时，没有崩溃日志是正常零异常结果，不是实验数据缺口。
- 不能仅因该文件不存在，就判断日志采集失败、实验结果不完整或崩溃结论不可信。
- 文件读取失败、格式损坏和实验中断需要按具体证据处理，不能套用本条规则掩盖问题。
- 结论针对本次实验，不扩展成应用在所有场景中都没有缺陷。这是内部判断边界，无需自动写成面向用户的免责声明。

### 报告输出要求

- 结果部分展示 Crash：0、ANR：0，详情为“无”，按用户语言表达。
- 不追加“崩溃日志缺失，但运行正常，因此按未检测到展示”等解释。
- 不追加“这不等于证明应用不存在崩溃”等泛化免责声明。
- 第九部分不因日志不存在而单独生成分析段落，也不将其列入数据缺口、风险或待验证事项。
- 如果用户主动询问统计依据，可以解释日志生成机制和本次 MCP 数据；正常报告不主动展开。

### 后续建议

无。不能仅因没有生成崩溃日志，就建议修复日志采集、补查日志或重新测试。

## KEA-GENERAL-001 · 纯随机测试的性质统计不适用

### 适用范围

通过 MCP 运行配置确认采用纯自动探索（纯随机／模糊测试），且没有加载 property 或 invariant 的实验。

### 专业知识

纯自动探索不执行用户编写的 property 和 invariant。因此，没有相关检查项、性质执行趋势为零属于正常情况，不表示性质执行失败，也不表示测试没有正常进行。

### 所需数据与判断条件

- 通过 `kea2_get_report` 的已保存启动参数或 `kea2_query_report` 的 `configuration` 核对本次运行配置，确认采用纯自动探索、未配置性质脚本。字段缺失本身不代表明确选择了纯自动探索。
- 通过 `kea2_query_report` 的 `checks` 核对检查项清单与该模式一致，没有 property 或 invariant；清单应可读，不能把来源缺失当成空清单。
- 不能仅凭检查项为空或执行次数为 0，就推断测试模式。
- 配置不明确、存在无法分类的检查项或数据相互矛盾时，先通过 MCP 核对，不强行应用本条规则。

### 分析规则

- 不将没有性质或不变量解释为测试异常。
- 不分析性质为何未执行、前置条件为何未满足。
- 不将全零的性质趋势解释为执行停滞或失败。
- 正常分析应聚焦探索步骤、覆盖情况、Crash 和 ANR。

### 报告输出要求

- 测试概要注明“测试模式：纯自动探索”。
- 性质通过数／总数显示“不适用”。
- 性质执行趋势仅写“不适用”，不展示全零趋势图或表。
- 性质违反详情仅写“不适用”。
- 在“性质与不变量执行统计”章节合并说明：“不适用，本次为纯自动探索。”不再分别输出两张空表或两段解释。
- 不重复说明清单为空、采样点全零、未知类型为零，也不追加“不代表执行失败”等解释。
- 第九部分不针对没有性质或不变量单独生成分析。
- 保留报告九部分结构，按用户语言表达；不适用的性质章节不影响其他结果的展示和分析。

### 后续建议

不因未配置性质测试而默认建议补充脚本或重新测试。用户明确提出业务性质验证需求时，再讨论性质测试方案。
