# Kea2 实验分析知识

适用于结果契约 1.5。每条知识都要与当前任务、当前快照中的 MCP 记录核对。知识编号用于内部核对解释依据；观测值须以 MCP 返回的检查项及来源为依据。报告默认使用易读的解释，仅在用户要求溯源时展示知识编号及来源标识。来源不完整时，结论仅限于可读记录。如有无法核对的条件，保留原因未确定。

## KEA-PROP-001 · Property 未执行

适用于 `checks` 中明确标为 `kind=property` 的记录。先确认统计来源可读、`executed` 明确为 0，再根据同一条记录的 `precond_satisfied` 解释。

| 前置条件满足次数 | 可支持的结论 |
| --- | --- |
| 0 | 本次可读记录中，既没有满足前置条件的记录，也没有执行记录。 |
| 大于 0 | 前置条件有过满足记录，但该性质没有执行记录。保留具体满足次数。 |
| 缺失或不可用 | 无法从现有统计判断前置条件是否满足。 |

仅凭这些计数不能确定页面是否到达、条件是否写错或调度是否异常。若问题涉及某个页面，可通过 MCP 查询 Activity 覆盖和步骤；只有在目标页面与该条件的关系有依据时才结合解释。

## KEA-INV-001 · Invariant 的 Fail 和 Error 均为零

适用于 `checks` 中明确标为 `kind=invariant`、且 `fail` 和 `error` 都明确为 0 的记录。可以写“该不变量在可读统计中没有记录到失败或错误”。数据源部分可读时注明范围；字段缺失时不作零值判断。

这些计数无法证明不变量检查过多少次、成功过多少次或在所有状态下都成立。任一计数大于 0 时，按检查项名称和 invariant 类型查询 findings，再根据需要读取异常详情。

## KEA-CRASH-001 · 无异常时不生成崩溃日志

### 适用范围

正常完成、MCP 返回 Crash 和 ANR 次数均为 0，且没有矛盾异常记录的实验。适用于纯自动探索和包含性质测试的实验。

### 专业知识

Crash/ANR 日志按异常产生。没有发生 Crash/ANR 时，不生成对应的 `crash-dump.log` 属于正常行为，该文件不是每次实验都必须存在的结果文件。

因此，可选日志不存在与日志读取失败、格式损坏是不同情况，不能仅凭 `availability.crashes=missing` 就判断采集异常。

### 所需数据与判断条件

- 通过 `kea2_get_report` 核对 `execution.status=completed`。
- `summary.observed_crash_occurrences` 和 `summary.observed_anr_occurrences` 均为 0。
- 通过 `kea2_query_report` 的 `findings` 分别核对 `type=crash` 和 `type=anr`，返回总数均为 0，且与概览属于同一快照。不能把尚未读取的记录当作不存在。
- 运行信息中没有与零异常矛盾的标记；若 `execution.finding_flags.crash_or_anr=true`，不应用本条规则。
- Crash/ANR 日志来源为 `available` 或 `missing`。计数为 null、来源部分可读、读取失败、格式损坏或记录矛盾时，不应用本条正常零异常解释，也不自行将未知计数改成 0。

### 分析规则

- 满足上述条件时，没有崩溃日志是正常零异常结果，不是实验数据缺口。
- 不能仅因该文件不存在，就判断日志采集失败、实验结果不完整或崩溃结论不可信。
- 文件读取失败、格式损坏和实验中断需要按具体证据处理，不能套用本条规则掩盖问题。
- 结论针对本次实验，不扩展成应用在所有场景中都没有缺陷。这是内部判断边界，无需自动写成面向用户的免责声明。

### 报告输出要求

- 结果部分展示 Crash：0、ANR：0，详情为“无”，按用户语言表达。
- 不追加“崩溃日志缺失，但运行正常，因此按未检测到展示”等解释。
- 不追加“这不等于证明应用不存在崩溃”等泛化免责声明。
- 第九部分不因日志不存在而单独生成分析段落，也不将其列入数据缺口、风险或待验证事项。
- 如果用户主动询问统计依据，可以解释日志生成机制和本次 MCP 数据；正常报告不主动展开。

### 后续建议

无。不能仅因没有生成崩溃日志，就建议修复日志采集、补查日志或重新测试。

## KEA-GENERAL-001 · 纯随机测试的性质统计不适用

### 适用范围

通过 MCP 运行配置确认采用纯自动探索（纯随机／模糊测试），且没有加载 property 或 invariant 的实验。

### 专业知识

纯自动探索不执行用户编写的 property 和 invariant。因此，没有相关检查项、性质执行趋势为零属于正常情况，不表示性质执行失败，也不表示测试没有正常进行。

### 所需数据与判断条件

- 通过 `kea2_get_report` 的已保存启动参数或 `kea2_query_report` 的 `configuration` 核对本次运行配置，确认采用纯自动探索、未配置性质脚本。字段缺失本身不代表明确选择了纯自动探索。
- 通过 `kea2_query_report` 的 `checks` 核对检查项清单与该模式一致，没有 property 或 invariant；清单应可读，不能把来源缺失当成空清单。
- 不能仅凭检查项为空或执行次数为 0，就推断测试模式。
- 配置不明确、存在无法分类的检查项或数据相互矛盾时，先通过 MCP 核对，不强行应用本条规则。

### 分析规则

- 不将没有性质或不变量解释为测试异常。
- 不分析性质为何未执行、前置条件为何未满足。
- 不将全零的性质趋势解释为执行停滞或失败。
- 正常分析应聚焦探索步骤、覆盖情况、Crash 和 ANR。

### 报告输出要求

- 测试概要注明“测试模式：纯自动探索”。
- 性质通过数／总数显示“不适用”。
- 性质执行趋势仅写“不适用”，不展示全零趋势图或表。
- 性质违反详情仅写“不适用”。
- 在“性质与不变量执行统计”章节合并说明：“不适用，本次为纯自动探索。”不再分别输出两张空表或两段解释。
- 不重复说明清单为空、采样点全零、未知类型为零，也不追加“不代表执行失败”等解释。
- 第九部分不针对没有性质或不变量单独生成分析。
- 保留报告九部分结构，按用户语言表达；不适用的性质章节不影响其他结果的展示和分析。

### 后续建议

不因未配置性质测试而默认建议补充脚本或重新测试。用户明确提出业务性质验证需求时，再讨论性质测试方案。
